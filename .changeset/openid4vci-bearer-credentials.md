Credentials without cryptographic holder binding (bearer credentials) can now be issued and received over OpenID4VCI. Both sides have to opt out of holder binding with `requireCryptographicHolderBinding: false`, the issuer per credential configuration and the holder per credential request. Presenting these credentials over OpenID4VP is not supported yet.

**Breaking:** on the issuer, each credential configuration now has to declare `proof_types_supported`, or set `requireCryptographicHolderBinding` to false. `createIssuer`, `updateIssuerMetadata` and `updateIssuer` throw otherwise. Issuers that are already stored keep issuing, a configuration without `proof_types_supported` still requires a `jwt` proof as before, but they can't be updated until every configuration declares its proof types or opts out.

A configuration with `requireCryptographicHolderBinding: false` is issued to a credential request without proofs, and a request for it that does contain a proof is rejected with `invalid_proof`. The option is not published in the issuer metadata, and can't be combined with `proof_types_supported`, `cryptographic_binding_methods_supported` or the `mso_mdoc` format, as an mdoc is always bound to a key. This only applies to OpenID4VCI 1.0 and draft 15 sessions, draft 11 to 14 sessions keep requiring a `jwt` proof.

**Breaking:** `holderBinding` in `OpenId4VciCredentialRequestToCredentialMapperOptions` is now optional. It is undefined for a credential request without proofs, for which the mapper must return a single credential that is not bound to a holder. Issuance fails when the mapper returns an SD-JWT with a `holder` or an mdoc for such a request. W3C JWT and JSON-LD credentials can't be checked, as they are only bound through their `credentialSubject.id`. `holderBinding` is always defined for a configuration that does not set `requireCryptographicHolderBinding` to false, but mappers have to handle the undefined case to compile.

On the holder, pass `requireCryptographicHolderBinding: false` to `requestCredentials` to accept credential configurations that declare neither `proof_types_supported` nor `cryptographic_binding_methods_supported`. No proof is sent and `credentialBindingResolver` is not called for those, the nonce is not fetched when none of the requested credentials need a proof, and an SD-JWT VC that turns out to be bound to a key is rejected, also when it is retrieved through the deferred credential endpoint. Without the option such a configuration is still rejected, now before anything is requested from the issuer. `credentialBindingResolver` is optional and only needed for credentials that require a proof.
