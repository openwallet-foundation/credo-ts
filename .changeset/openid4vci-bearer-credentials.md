Credentials without cryptographic holder binding (bearer credentials) can now be issued and received over OpenID4VCI. Nothing changes by default: the issuer keeps requiring a proof and the holder keeps refusing credential configurations that need none. Both sides have to opt out with `requireCryptographicHolderBinding: false`. Presenting these credentials over OpenID4VP is not supported yet.

On the issuer, set `requireCryptographicHolderBinding: false` in the issuer module config. A credential configuration that declares neither `proof_types_supported` nor `cryptographic_binding_methods_supported` is then issued to a credential request without proofs, and a request for it that does contain a proof is rejected with `invalid_proof`. The option applies to every issuer of the agent, so make sure all configurations that must stay bound declare `proof_types_supported` before disabling it. This only applies to OpenID4VCI 1.0 and draft 15 sessions, draft 11 to 14 sessions keep requiring a `jwt` proof. An mdoc is always bound to a key, so an `mso_mdoc` configuration without `proof_types_supported` keeps requiring a proof, and can't be created or updated anymore once the option is disabled.

**Breaking:** `holderBinding` in `OpenId4VciCredentialRequestToCredentialMapperOptions` is now optional. It is undefined for a credential request without proofs, for which the mapper must return a single credential that is not bound to a holder. Issuance fails when the mapper returns an SD-JWT with a `holder` or an mdoc for such a request. W3C JWT and JSON-LD credentials can't be checked, as they are only bound through their `credentialSubject.id`. `holderBinding` is always defined as long as `requireCryptographicHolderBinding` is not disabled, but mappers have to handle the undefined case to compile.

On the holder, pass `requireCryptographicHolderBinding: false` to `requestCredentials` to accept credential configurations that declare neither `proof_types_supported` nor `cryptographic_binding_methods_supported`. No proof is sent and `credentialBindingResolver` is not called for those, the nonce is not fetched when none of the requested credentials need a proof, and an SD-JWT VC that turns out to be bound to a key is rejected, also when it is retrieved through the deferred credential endpoint. Without the option such a configuration is still rejected, now before anything is requested from the issuer. `credentialBindingResolver` is optional and only needed for credentials that require a proof.
